# Inventory radiation: dependency audit and acceptance gate

Status: **NOT ACCEPTED / gameplay not tested**. Source audit, 2026-10-19. No production code or build was changed/run for the initial audit; the subsequent utility-only progress is recorded below. Native machine-inventory/battery probes are not evidence of player irradiation working.

## Subsequent utility-only progress (2026-10-19)

`util/ItemStackUtil.java` has now been migrated as a complete native utility class, including the empty-loaded-record filter identified below. Its standalone native probe passes 532 assertions for copy/count/NBT/registry/JSON and real native World/EntityItem spill fixtures; see `tests/item-stack-util-migration-notes.md` and `continuation-2026-10-19/item-stack-util-native-probe.log`. The spill snapshots final-stack identity/NBT before native count reaches zero. This closes a utility dependency only: no player tick, hazard transformer, protection, entity-data lifecycle or gameplay gate is accepted by these tests. All checklist items remain unchecked. The initial audit findings below describe the original contracts and the remaining consumers; the mechanical-loader risk is now explicitly handled in this utility.

## User-facing engineering acceptance

Радиация от предметов в инвентаре входит в обязательную готовность порта, а не в необязательные улучшения после выпуска. Сейчас проверены зависимости по исходникам; работоспособность в Minecraft 1.12.2 ещё не подтверждена. Перенос машинных слотов не заменяет перенос тика игрока, защиты и сохранения дозы. До заявления «готово» нужны проверки переноса/удаления предмета, количества, защиты, containment box, разделения стека и загрузки NBT. Все эти игровые проверки ниже остаются открытыми.

## Original-to-current call path and actual semantics

Paths below are relative to `src/main/java/com/hbm/`. Compare with the same paths in `../ntm-original-pristine/`.

- `main/MainRegistry.java:296-297`: registers hazard items and transformers. `hazard/HazardRegistry.java:593-597` always adds the radiation-NBT transformer; container transformer is omitted when **both** `enableLBSM` and `enableLBSMSafeCrates` are true. This is a configuration-wide exception, not intrinsic shielding of every crate.
- `main/ModEventHandler.java:onPlayerTick`, server `START` branch at approximately 1386, activation fallback at 1476-1485, `HazardSystem.updatePlayerInventory(player)` at 1488. No radiation scan is driven by the machine inventory base. Main and armor inventories are scanned by `hazard/HazardSystem.java:197-217`; original has no offhand inventory. Native offhand policy needs an explicit compatibility decision and tests, not accidental omission/double counting.
- `HazardSystem.applyHazards` -> `getHazardsFromStack` -> registry/ore-dictionary/stack matching and transformers -> `HazardEntry.applyHazard` -> modifiers -> `hazard/type/HazardTypeRadiation.java:onUpdate`.
- For each radiation entry, `onUpdate` multiplies its evaluated level by stack count, then adds `ntmNeutron` if present, divides by 20, applies reacher attenuation, and calls `ContaminationUtil.contaminate(...RADIATION, CREATIVE, rad)`. With `enable528`, reacher divides by 49; otherwise it applies `BobMathUtil.squirt`. This is per-entry/per-stack, so do not assume splitting preserves total exposure when nonlinear reacher protection is active.
- `util/ContaminationUtil.java:270-316`: updates environmental reading before immunity checks; creative mode and player age below 200 ticks prevent accumulated dose. Radiation immunity also prevents dose. Ordinary carried radiation uses `CREATIVE`, not a binary hazmat-suit exemption. Dose multiplier is `10^(-HazmatRegistry.getResistance(player))` (`calculateRadiationMod`, lines 33-45).
- `handler/HazmatRegistry.java:168-217`: resistance sums worn armor and cladding, with applicable player/potion bonuses. Reacher, armor, cladding and radx are distinct mechanisms. `extprop/HbmLivingProps.java:82-106` stores/clamps dose and respects `enableContamination`; persistence uses `hfr_radiation` in save/load methods. `EntityEffectHandler` consumes that dose for effects. Removing the item stops its subsequent contribution, **not** an immediate reset of accumulated dose; no passive decay is promised here.

### Containers and NBT are not generic shielding

`hazard/transformer/HazardTransformerRadiationContainer.java:24-89` recognizes only storage-crate blocks, containment_box, plastic_bag and toolbox. Toolbox reads 24 slots; containment box 20; bag 1 via `ItemStackUtil.readStacksFromNBT`. Crates read `slot0` through `slot103`. Each sums `getHazardLevelFromStack(child, RADIATION) * child.count`; containment box applies `squirt(sum)`, bag multiplies by 2, toolbox/crate have no attenuation in this transformer. `squirt(x)` is `sqrt(x + 1/(x+2)^2) - 1/(x+2)` (`util/BobMathUtil.java:250`). A containment box reduces this source, not necessarily to zero. A placed machine/block is not automatically covered by this carried-item transformer.

Important original behavior to preserve or explicitly resolve, not silently simplify:

- `HazardTransformerRadiationNBT.transformPost` always appends an entry, including zero; it reads `hfrHazRadiation` and `ntmNeutron`. `getHazardLevelFromStack` returns **the first matching entry**, whereas `applyHazards` applies **all** entries. The radiation handler also adds `ntmNeutron` per radiation entry, and the player tick has an activation fallback. Nested containers/NBT activation therefore require original-result fixtures; one tooltip or one presumed linear formula is not an oracle.
- `ItemStackUtil.java:148-169` uses `items` list plus signed-byte `slot`, nullable arrays, and loops to requested capacity, obtaining empty compounds for absent list entries. Native deserialization yields `ItemStack.EMPTY` rather than legacy null. A mechanical loader substitution without `isEmpty` filtering could overwrite a real slot 0 with default empty records. Test sparse/default/invalid/duplicate entries explicitly.
- Crate item persistence (`blocks/generic/BlockStorageCrate.java:128-145,228`) uses separate `slotN` compound keys. It is not interchangeable with machine `items`/`slot` NBT.

## Native blockers and relation to current inventory edits

The audited hazard logic is still essentially original: HazardSystem changed only side imports; the two container/NBT transformers are byte-identical to pristine; HazardTypeRadiation changed imports/formatting names, not behavior. Source still uses legacy array length/index access, `stackSize`, `stackTagCompound`, `loadItemStackFromNBT`, `inventory.hasItem`, and equipment APIs. `items/ItemInventory.java` is also still a legacy IInventory implementation. `HbmLivingProps` still imports/implements removed `IExtendedEntityProperties` and calls entity extended-properties methods; existing `porting/continuation-2026-10-19/native-coordinate-clean-compile.log` reports the missing type. Native entity data lifecycle/persistence/sync is an independent blocker, not solved by tile NBT.

Current `tileentity/TileEntityInventoryBase.java` deliberately keeps nullable internal `slots`, returns EMPTY at native getter/removal boundaries, preserves live nonempty stack references, and normalizes EMPTY setters/loads back to null. It does not scan the player, calculate dose, or edit hazard tags. Thus there is no direct change to the radiation formula from this work. There **is** integration risk in old consumers that still check getter results only against null, and in transfer/split/load paths losing or duplicating the authoritative count/NBT. `BlockStorageCrate` harvest currently checks `getStackInSlot(i) == null`, illustrating the boundary risk. Keep nonempty aliases live; normalize emptiness without manufacturing placeholder stack tags or mutating shared EMPTY. Machine readFromNBT retains legacy overlay behavior rather than clearing every omitted slot; test existing-object reload separately from a fresh load.

## Required evidence before declaring ready

All gates are deliberately unchecked. Use matched original/current registry/config fixtures, record item IDs/counts/full relevant NBT, tick phase, player age, armor, reacher and dose deltas. Isolate carried-source exposure from chunk radiation, activation, treatment and other effects.

- [ ] Native compilation/integration of hazard registry, tick hook, player inventory iteration, protection and entity-data persistence/sync. Verify exactly one server START application, no client duplication; cover hotbar, main, armor, and explicitly chosen offhand behavior.
- [ ] Carry/remove: mature survival player, clean environment, untagged registered radioactive item. Carry adds expected dose; empty slot/EMPTY does not. Transfer to storage/remove stops further **item** contribution next scan without deleting accumulated dose. Client display agrees with authoritative state.
- [ ] Quantity: identical ordinary untagged item at counts 1 and N, no reacher or changing modifiers. Confirm per-entry count scaling and total over 20 server ticks below dose cap. Count zero never reaches division/activation or generates a hazard.
- [ ] Protection: compare bare player vs known resistance armor/cladding and radx; verify actual resistance multiplier. Test reacher separately in each relevant enable528 mode; creative and first-200-tick immunity separately. Do not equate environmental reading with accumulated dose.
- [ ] Containment box: matched contents loose vs boxed, then remove contents and reload. Verify original squirt attenuation, not zero exposure. Controls: toolbox/crate sum, bag multiplier, transformer-enabled/disabled configs. Nested containers get original-result fixtures, not extrapolation.
- [ ] Split/merge/transfer: preserve item/meta/count/tags across player and machine slots, drag/shift-click and actual supported automation. No stale slot alias, duplication, ghost irradiation or EMPTY mutation. Untagged unprotected totals should conserve quantity; tagged/reacher cases must match original per-stack behavior rather than assumed conservation.
- [ ] NBT: fresh/save/reload and existing-object reload; hfrHazRadiation, ntmNeutron, cladding, nested contents and player hfr_radiation survive supported persistence paths. Test no tag, empty compound/list, sparse slots, out-of-range signed-byte slots, duplicate slot entries and crate slotN format. Confirm missing tags/default records cause neither phantom radiation nor erasure of real contents.
- [ ] Actual 1.12.2 in-game server/client run of the above after native blockers are removed, plus restart/rejoin persistence and packet consistency. Attach reproducible results before checking any gate; inventory/battery source or boundary tests alone do not satisfy this gate.

## Dropped items: original-source audit (2026-10-19)

User requirement: «При выпадении предметы кстати тоже должны облученными лежать». This requires distinguishing retention of radioactive/activated item properties from a dropped entity actively irradiating its surroundings. Neither is established by the utility spill probe alone.

### Verified path and limits

- Current `main/ModEventHandler.java:866-925` (`worldTick`) copies loaded entities on the server and, on `Phase.END` when world time is divisible by `max(1, ITEM_HAZARD_DROP_TICKRATE)`, calls `HazardSystem.updateDroppedItem` for each EntityItem. The pristine equivalent is at approximately 862-921. `config/ServerConfig.java:22` defaults this interval to **2**. This is distinct from the player inventory's server START handler.
- In pristine and current `hazard/HazardSystem.java:229-239`, `updateDroppedItem` gets the entity's stack, rejects dead/null/item-null/nonpositive-count inputs, resolves all hazards and modifiers with a null living entity, then calls each hazard type's `updateEntity`. It does not itself irradiate nearby players or add chunk radiation.
- Crucially, **both pristine and current `hazard/type/HazardTypeRadiation.java:52` and `HazardTypeNeutron.java:62` implement `updateEntity(EntityItem, float)` as an empty method**. The generic original dropped-item hazard path therefore does not emit ordinary radiation or neutron activation into the surroundings. Do not claim that migrating this dispatcher restores a universal ambient-radiation field which these original handlers never implemented.
- Radioactive properties are not exclusively NBT: normal item/ore/meta registration supplies hazards, while `hfrHazRadiation` and `ntmNeutron` supply additional state through the previously audited transformers. Preserve identity, metadata, count and applicable tags on drop/pickup; merely adding a custom “radioactive” tag would neither preserve this model nor implement an original emission mechanism.
- Some items have their own Forge `onEntityItemUpdate` or custom-entity behavior. `items/special/ItemNuclearWaste.java:13-32` uses `EntityItemWaste`, effectively unlimited item lifespan, preserved motion, and pickup delay 10; `entity/item/EntityItemWaste.java:22-29` supplies invulnerability/damage rejection, **not a radiation tick override**. These two files are byte-identical to pristine at audit time. Examples bound to this class include trinitite and nuclear waste (`items/ModItems.java:3841,3850-3853`). Do not mislabel invulnerability/long lifespan as environmental radiation.
- `items/special/ItemDemonCore.java:17-25` replaces the open core with a new closed-core stack when grounded server-side and drops a screwdriver. `ItemDigamma.onEntityItemUpdate`, `ItemDrop.onEntityItemUpdate`, and `items/weapon/WeaponizedCell.onEntityItemUpdate` have special drop-triggered transformations/destruction/explosions. Those item-specific effects are not evidence for a generic radiation radius, and transformations intentionally creating new stacks need their own original-parity expectations rather than a blanket assertion that every drop always retains every tag.
- `main/ModEventHandler.onLivingDrop` writes `ntmContagion` for contagious entities; this is not the radiation/activation tag and must not be conflated with it. Audited toss/pickup handlers do not add a generic dropped radiation field. Existing chunk radiation handlers contain no EntityItem scan establishing such a field.

The dispatcher, special items and custom waste entity still expose old EntityItem/World APIs. This read-only audit does not migrate them, run their ticks, demonstrate entity NBT roundtrips or establish live pickup/merge semantics. The native ItemStackUtil test verifies constructed spilled stacks and the captured spawn call only; its world deliberately does not perform real spawn lifecycle, merge, save/reload or nearby-player irradiation.

### Cross-check outside the generic callbacks

Scope is the supplied `ntm-original-pristine` archive and current port tree, **not every upstream NTM version or add-on**. A source cross-check of Java files mentioning EntityItem together with direct radiation mutation/chunk APIs found the hazard handlers and ModEventHandler above, plus these unrelated paths in pristine:

- `handler/EntityEffectHandler.java:297-339` reads chunk/dimension/celestial radiation and a **living entity's** own neutron activation, then applies exposure to that living entity. Its EntityItem branch at 515-522 sets `ntmContagion` during disease transmission, not radiation emission. Biome exposure at 127-135 is also independent of a dropped stack.
- `items/armor/ArmorFSB.java:395` excludes item entities from hard-landing effects; its chunk-radiation read at 452 is a separate player HUD path.
- `tileentity/machine/TileEntityFEL.java:116` applies gamma-beam exposure, while its EntityItem construction at 153 drops a machine block after destruction. This does not turn the dropped machine item into the beam source.
- The remaining archive `onEntityItemUpdate` overrides include `ItemRag.java:19` (water conversion) and `items/armor/ArmorHat.java:19` (deletion), besides the special items listed above. Radiation-producing projectile/mob/explosion entities exist elsewhere, so the bounded conclusion is **no generic dropped-stack ambient source found in the inspected paths**, not that this mod never irradiates nearby entities after any possible drop-triggered event.

### Additional unchecked gates

- [ ] **Drop persistence:** from hotbar/main inventory, manual toss and machine spill, verify ordinary registered radioactive items and separately NBT-activated items retain the correct item/meta/count/hazard tags while lying in the world. Include original special-item substitutions/custom entities as separate cases, not ordinary invariant stacks.
- [ ] **Pickup:** after dropping and waiting, collect the surviving original-equivalent stack; verify carried radiation resumes from its actual identity/entries/count/tags with no tag loss, double application or stale source. Isolate accumulated player dose from newly applied exposure.
- [ ] **Merge/split:** compatible dropped stacks merge with correct total count and state; nonmatching radiation/activation NBT is not silently combined or overwritten. Test overflow/maximum stack size, split then remerge, and special custom-entity behavior against original observations. Do not assume a count-weighted activation average or special merge policy not present in the original.
- [ ] **Entity save/reload:** actual dropped EntityItem/custom waste entity survives supported chunk unload/reload and server restart with identity, count and relevant tags intact, and still has original-equivalent pickup/lifespan/invulnerability behavior. No resurrection of consumed/dead sources or loss of hazard state.
- [ ] **Dropped dispatcher:** native server END scheduling respects configured interval and dead/empty rejection; there is no client duplication. Demonstrate item-specific callbacks and original no-op generic radiation/neutron callbacks independently.
- [ ] **Nearby irradiation / explicit behavior decision:** in a clean original/current comparison, measure nearby player's dose and chunk/environment readings while an ordinary radioactive/activated item is on the ground, without picking it up. The audited generic original callbacks predict **no added ambient effect through this path**. If the requested outcome is that every dropped radioactive item also irradiates nearby players, retain that requirement as an explicit behavior addition/decision, not as already implemented source parity; define its intended behavior with the user before inventing radius, falloff, shielding, stack scaling, chunk deposition or cleanup rules. Special explosive/transforming items must not contaminate this ordinary-item control.

None of these gates is satisfied by NBT retention alone. No generic ground-emission behavior was added in this audit.
